# PR review — verified findings, unambiguous comments

Arguments: `$ARGUMENTS` — a PR number or URL (if omitted, run `gh pr list` and ask which one), plus optionally one of `--post` (publish the review to GitHub after composing it) or `--stage` (create it on GitHub as a **pending draft review** — nothing reaches the PR author unless the user submits it from the GitHub UI; Step 5 owns the semantics and mechanics). If both flags are passed, stage — it is the reversible reading of an ambiguous ask.

## Step 1 — Gather

- `gh pr view <n> --json title,body,author,baseRefName,headRefName,state,additions,deletions,changedFiles,mergeable,mergeStateStatus,statusCheckRollup,url,createdAt,closingIssuesReferences`
- `gh pr diff <n>` for the diff; fetch the branch locally: `git fetch origin <base> 'pull/<n>/head:pr-<n>'`
- **Read the problem the PR claims to solve, not only the PR.** `closingIssuesReferences` above lists the issues the merge will auto-close (from `Fixes #N` / `Closes #N`); read each one *with its comments* — `gh issue view <m> --comments`. Plenty of projects track elsewhere: an OpenMRS PR usually carries a JIRA key in its title or branch name (`TRUNK-6429`, `O3-1234`), and the ticket is readable without auth at `https://openmrs.atlassian.net/rest/api/2/issue/<KEY>?fields=summary,description,status,comment` (the `issues.openmrs.org` link people paste redirects to a dashboard and won't serve REST). Step 2 is what this feeds.
- Check whether the PR is behind its base: `git diff origin/<base>...pr-<n> --stat` vs `git diff origin/<base> pr-<n> --stat` (if they differ, note the drift).
- **Read the existing review conversation before reviewing** — `gh api repos/<owner>/<repo>/pulls/<n>/comments --paginate` (inline threads, with `in_reply_to_id` and author replies) and `gh pr view <n> --json reviews,comments`. A PR is often mid-conversation: a prior round may have raised your finding already, and the author may have replied/fixed it on a newer commit. For each candidate finding, check it against those threads — if it's already open, **reply in that thread** (build on it, or note the sub-point still unaddressed) instead of posting a fresh top-level comment. Duplicating a live thread is exactly the noise that makes review a bottleneck.
- **Check for the user's own pending review on every round** — `gh api repos/<owner>/<repo>/pulls/<n>/reviews --paginate --jq '.[] | select(.state == "PENDING")'`. A prior `--stage` round the user never submitted (or a review they hand-started in the UI) holds draft comments invisible to `/pulls/<n>/comments` — read them via `.../reviews/<id>/comments --paginate` — and it blocks any new review create on the PR (staged or posted, the create 422s). If one exists, surface it and get the user's decision **before composing**, because the drafts' fate forks the round: the call is theirs — they submit it in the UI, or ask you to discard it (the DELETE in Step 5). Submitted → the drafts are now published threads; treat them like any prior round's comments (reply in-thread or stay silent, per the bullets above and below). Discarded → the drafts are gone; re-raise in your own round whatever still holds.
- **Verify claimed fixes against the head — "fixed" is a claim, not evidence.** When a prior thread is marked resolved or the author replied "done/fixed", read the current code at that spot rather than trusting the reply. Authors routinely fix the headline of a comment while leaving a sub-point untouched (e.g. "memoized the value" addresses re-querying but not the broad `catch` the same comment flagged). If the fix is real, **leave the thread closed and post nothing** — no reply, no "thanks, that's fixed", no resolved-thread acknowledgment. Silence *is* the confirmation: GitHub already shows the author that their commit addressed the comment, so re-commenting to say so is pure noise, and it is the single most common re-review slop. Only when a flagged sub-point *survives* do you reply in-thread — and that reply carries **only** the surviving sub-point and its fix, never a preamble crediting the parts that were resolved. For a re-review of an updated PR, diff against the commit you last reviewed (`git diff <last-reviewed-sha>..pr-<n>`) to focus on what changed, but still confirm each prior finding is genuinely resolved in the head — and confirm it *silently*, by not commenting.
- **A comment is filed against a commit, not the head — check that commit before calling it stale, wrong, or a false positive.** Compare the comment's `commit_id`/`original_commit_id` to the PR head; if they differ (a null `line` alongside a set `original_line` is the tell that the code moved under it), diff those two commits for that file and reproduce what the commenter saw before judging. A quiet followup commit can fully resolve a real finding, which then reads as a false positive when you only look at the head — the code changed, the commenter was not wrong. This applies with full force to bot comments (Copilot and the like): a valid catch that the author already fixed is *still* not a false positive. An already-resolved finding earns silence: never a "false positive" rebuttal, and never a "good catch, fixed" note.

## Step 2 — Is this the right fix, and the best one available?

Line-level review of code that shouldn't exist wastes both sides' time, so settle the approach before verifying the details. Two questions, in order: does the change resolve the problem it claims to, and is this the *best* way available to resolve it rather than merely *a* way that works?

**Work out what problem it solves**, from what Step 1 gathered, in that order of authority: the linked issue and its thread, then the PR description, then the title. The thread carries as much as the issue body — maintainers redirect approaches in comments ("don't add a global property for this, read it from runtime properties"), and a PR that walks past that redirect is the clearest approach finding there is. If the tracker was unreachable, review what you can and say in your report that you judged the change without the ticket, rather than writing as though the ticket agreed with it. If no problem statement exists anywhere and the diff doesn't speak for itself, ask — that's usually the highest-value comment on the PR. Don't make it a reflex, though: an obvious change (a parent-POM bump, a typo in an error message) needs no ticket, and a standing "please link an issue" nit is process noise.

**Does it actually resolve that problem?** A different question from "is the code correct", and a PR can pass every line-level check while failing it. The strongest evidence is the issue's own reproduction: run it against the PR branch and against the base, and expect failure on base and success on the PR — the bar the test-coverage section applies to behavior changes.

With no ticket and no repro, the PR's own description becomes the acceptance criteria. A "key guarantees", "review focus", or "what changed" list has told you exactly what to test, and working through it one claim at a time is the highest-yield pass available. Read each guarantee as the general statement it is rather than as a description of the diff: "a handled backend failure cannot be reported as a complete chart" is a claim about every backend, and the one the author just fixed is the least likely to be the one that breaks it. Those lists are also where an author writes down what they believe rather than what they checked, so a guarantee with no test behind it is worth probing even when the code on the screen looks right.

Ways a technically-correct change misses:

- it fixes the path in the issue's stack trace while the reported symptom also arrives by another path;
- it corrects the symptom and leaves the cause producing it (normalizing at read time while the bad value keeps getting written);
- it handles the literal example in the ticket rather than the class of input that example stands for;
- it resolves part of a multi-part ticket and closes the whole thing.

A change that doesn't resolve the issue it closes is blocking, and it's the finding most often missed, precisely because everything at the line level checks out.

**Does it do only that?** The mirror of the question above, and the easier one to skip, because every extra hunk is by construction something that works. Account for each hunk as required by the ticket or not, and treat what isn't as something to take out: a format-on-save sweep over untouched code, a drive-by rename, a cleanup spotted in passing. Verifying that such a change is harmless is not a reason to let it merge — it is the reason it sails through, and the proof cost has already landed on the reviewer. That cost is the point: on append-only files above all (migrations, changelogs, generated resources), a diff that only ever grows lets the next reviewer see at a glance that nothing already shipped was disturbed, and once old entries have been rewritten somebody has to establish that separately, which is the first thing dropped under time pressure.

Quantify before commenting, because the size is the argument: `--stat` on the diff against the same diff with `--ignore-all-space` isolates whitespace-only churn, and a per-block text compare names which entries were touched. Then say plainly what you confirmed is safe, so the author doesn't hunt for damage that isn't there, and name the cost as review time instead of manufacturing a failure mode. Absent a failure mode this isn't blocking, but not blocking is not the same as not worth raising: this is the one class of finding where a clean verification result argues *for* the comment rather than against it. It does not contradict the anti-pattern about critiquing an inflated version of the PR — that one stops you demanding the PR deliver *more*, this one stops it shipping *extra*.

**Is it the best available fix, or just one that works?** Working is the floor, not the bar — a change can resolve the issue, pass CI, and still be the wrong way to have got there. This is also the judgment the author is least able to make for themselves: by the time they open a PR they've stopped seeing the approaches they didn't take. So make the comparison explicit rather than scanning for smells. **Name the one or two approaches a maintainer of *this* codebase would have weighed, and say what makes the chosen one better or worse than each.** If you can't name a single alternative, you haven't reviewed the approach yet — you've only checked it against a list.

The codebase itself is the best evidence of what "best" means here, and it's cheap to consult: `git log` and `git grep` for how this class of problem was already solved in the tree, then judge the PR against its nearest sibling. That turns the objection into something checkable — "the other three importers all resolve the concept by uuid, and this one parses the name" is an argument the author can go and read, where an appeal to general good practice is one they can only agree or disagree with. A divergence from the sibling isn't automatically wrong; it's the thing that has to be justified, and asking what justifies it is a fair review comment on its own.

The wrong-shape signals, each a finding only once verified rather than merely suspected:

- it re-implements something the framework or the codebase already provides (an existing hook, extension point, or utility). Confirm the alternative exists *and* reaches this case before naming it: Step 3's rules on absence claims and cited precedent apply at full force, because "there's already a hook for that" is exactly the confident-and-wrong claim that burns author trust;
- it works around a constraint by bypassing the layer that enforces it;
- it special-cases one caller where the shared path is what's broken, or changes shared behavior for one caller's benefit — then name the other callers and what they get;
- it duplicates state or logic, so there are now two places to drift apart;
- it contradicts a written architecture decision, where the repo keeps one (here, `docs/adr.md`) — cite the decision rather than re-arguing the design from scratch;
- it fixes this instance in a way the next instance will need repeated, when a general fix was available.

**Works, but hacky** is the other half, and the one a correctness-focused review skips by construction, because everything it looks at passes. The tells sit below the architecture, in how the result is reached:

- reflection, string parsing, or `toString()` comparison where a typed API exists;
- a sleep, a retry, or a poll standing in for the real synchronization or lifecycle hook;
- catching and swallowing to make a symptom disappear (the silent-failure rule in Step 4 applies with force);
- an existing method copy-pasted so one line could change;
- a check disabled or loosened — a test ignored, a validation skipped, a lint rule suppressed — instead of satisfied;
- a magic constant mirroring a value defined upstream, with nothing tying the two together;
- production code carrying a branch that exists only to make a test pass;
- `instanceof` chains or type switches where the surrounding code dispatches polymorphically.

The mirror image counts too, and is harder to say out loud because it looks like craftsmanship: an abstraction, a config knob, or a strategy interface built for a second case that doesn't exist; two hundred lines where twenty would do; a framework grown to fix one bug. Best is *proportionate*, not maximal — a hack and a cathedral are both the wrong size for the problem.

**The bar for saying "not like this".** An approach objection is worth posting only when you can state both halves: the concrete alternative, and the concrete cost of what's here — same shape as a failure-mode sentence, naming what breaks or what work it creates, and for whom. Cost missing, it's taste; keep it to yourself. Alternative missing, you have a concern rather than a finding, so ask it as a question. "This isn't how I'd have structured it" and "this feels hacky" are not findings — and the second is the objection authors resent most, because there's nothing in it to act on. "This duplicates the mapping in `X`, so the two drift the first time either changes" is a finding; so is "parsing the display name to get the uuid breaks the moment someone renames the concept, and `getUuid()` is right there". Maintenance is a real cost, not a soft one: *whoever changes X next has to remember to change Y* names it as concretely as a stack trace. Keep the disposition proportionate, though — hacky-but-working is normally a non-blocking suggestion, and it blocks only when the hack has a failure mode of its own or when the cleanup provably won't happen once this merges. When the cost is real but the better approach is bigger than the PR, say so and keep it non-blocking — the anti-pattern about inflating the PR still governs. The line to hold: *doesn't solve the problem, or solves it in a way that will hurt* gets raised now; *I would have built more* is a follow-up at most.

**On approach, you are the likeliest one to be wrong.** Correctness findings are checkable against the code; approach findings run on context the diff doesn't carry, and the author has more of it than you do. "They'd have used the obvious API if it worked" is a live possibility — they may have tried it and hit something invisible from here. So where the answer would change your finding, ask before asserting ("was there a reason `getUuid()` doesn't work here?"), and when the reason turns out to be real, what the PR needs is usually a comment in the code recording it, not a rewrite. Keep the comparison itself to yourself, too: weighing three alternatives is how you reach the judgment, not what you post. The review carries one recommendation and its cost — never a tour of the options you considered, which is the same architecture-grading the body rules ban in Step 4.

**The ticket is evidence, not a spec.** Issues go stale, and the fix an issue proposes is sometimes worse than the one the author found. Judge against the underlying problem: a PR that solves it differently from what the ticket proposed is fine, and a PR that does exactly what the ticket asked while leaving the problem standing is not. When the ticket itself is the thing that's wrong, say so in the review instead of holding the PR to it.

**When the approach really is in question, lead with that and stop stacking line-level comments.** Twelve nits on code that may not survive a rewrite are noise, and they bury the one comment that decides the PR. Post the approach finding plus whatever would survive the rewrite, hold the rest, and say you'll do the detailed pass once the direction is settled. When the approach is sound, say nothing about it: an approach you agree with earns no comment, exactly like any other cleared concern (Step 4). And on a re-review, an approach already argued out — the author answered, or a maintainer endorsed it in the thread — is closed. Reopen it only if the head commit changed the approach, or new evidence overturns the answer that closed it; "I'd still have done it differently" a round later is the worst kind of review noise, because it costs the author a rewrite argument they already won.

## Step 3 — Verify, don't just read

Findings must be grounded in evidence, scaled to what the change touches. **The same bar applies to thread replies and design answers, not only to findings.** A sentence answering "is this approach OK?" or "what happens if X?" asserts behavior exactly as hard as an `issue:` does, and the author acts on it just as hard — harder, because it arrives as the answer to their own question. It is also the likeliest place for the discipline to lapse, since a reply feels like conversation rather than a claim. If a reply asserts what the code or framework does, run it before posting.

- Always read the full files being changed (not just the hunks), and `git grep` the whole tree for symbols/properties the PR renames or removes — silent breakage hides outside the diff (e.g. filtered resources referencing a renamed Maven property).
- Build-config changes (pom.xml, Gradle, CI): build both the base branch and the PR branch in throwaway worktrees (`git worktree add --detach /tmp/<name> <ref>`), then compare: test counts per module, produced and installed artifacts (watch for attached artifacts like `-tests.jar` that downstream consumers depend on), `mvn dependency:tree` diffs, and packaged-archive entry lists plus filtered resources (`unzip -Z1`, `unzip -p ... | diff`). Remove the worktrees afterwards (`git worktree remove --force`).
- Parent-POM or dependency upgrades: download the new parent/dependency POM and confirm that everything deleted locally is actually provided upstream (dependencies vs dependencyManagement, plugin executions, properties, distributionManagement). Check published artifacts on the repository (e.g. `curl -sL .../maven-metadata.xml`) when removal of an attached artifact would break consumers.
- Claims about runtime behavior: run the relevant tests instead of asserting from code.
- A search hit inside a method proves the call exists *somewhere* in it, never that it is on the path you care about. Before asserting what a framework does for a given call, read the enclosing method top to bottom and name the branch your path actually takes; sibling branches routinely disagree. (OpenMRS `RequiredDataAdvice.before` calls `ValidateUtil.validate` on the `save*`/`create*` branch and not on the `void`/`unvoid`/`retire`/`unretire` branch, so "the advice validates" is true or false purely by method name. A `-A 6` grep window shows you the first fact and hides the second.)
- Absence claims ("nothing registers X", "the framework never does Y") must be positively verified against the dependency's **sources** — a local checkout of the dependency (check sibling directories of the repo) or its upstream repo at the ref the project actually builds against — never inferred from jar scans or config-file greps alone: annotation-registered/component-scanned beans are invisible to XML inspection, and installed SNAPSHOT artifacts can lag or lead the sources.
- A zero-hit search is evidence only after a positive control: before trusting "no matches", prove the same pipeline finds a string you know is present (e.g. `java/lang/Object` in a class file). Shell `grep` may be shadowed by an alias/function (ugrep shims silently skip binary-ish input, e.g. `strings` output of class files) — for evidence-grade searches use `command grep`, `git grep`, or the dedicated search tools, and never add `2>/dev/null` to an evidence-gathering command.
- When the one experiment that could falsify a finding can't run (build stopped, environment unavailable), the finding ships as a `question:`, not a fact — and a "confirmation" that structurally cannot fail (a standalone repro that omits the very component in question) is not verification.
- Before posting, re-read every claim against the facts you already gathered this session and hunt for the one that contradicts it. The cheapest false claim to catch is the one whose refutation is already on your screen — citing an upstream precedent whose own schema makes the cited behavior unreachable, while having read that schema an hour earlier. A claim that survives only because you never connected it to something you already know has not been verified. This applies with most force to a precedent cited *in support of* a recommendation: check that the precedent actually reaches the state you are claiming it demonstrates.

### Dimensions to sweep

Cover each of these, scaled to what the PR touches — an unnamed dimension is one you'll silently skip: **solution fit** (does it resolve the reported problem, and by the best approach available rather than merely one that works — Step 2), **correctness** (verified, not eyeballed), **test coverage** (section below), **security** (input validation, authorization checks, secrets in diffs or CI config, injection, unsafe deserialization), **performance** (N+1 queries, work added to hot paths or loops, blocking calls, unbounded growth), and **project conventions** (the change should read like the surrounding code — but don't flag what CI formatters already enforce).

### Trace outward — the bugs live outside the diff

The diff is a piece of a bigger machine; review the machine, not the patch. Follow each thread at least one level out from the changed lines:

- **Unchanged neighbors.** Re-read the unchanged code, comments, Javadoc, and docs adjacent to or depending on the change — anything stating an assumption ("the only caller", "X is the only path that…"). Ask of each: does this PR make that statement false? Diff-scoped review structurally cannot catch these, because the now-stale line never appears in the diff.
- **Consumers and published artifacts.** For everything the changed code produces — events fired, attached/published artifacts (e.g. `-tests.jar` classifiers), API responses, filtered resources — identify who consumes it, in-repo and downstream, and verify the contract still holds.
- **Optional dependencies and lifecycle.** For `provided`-scope deps, soft module references (`aware_of_module`), and registration-order-sensitive code (Spring beans, listeners, schedulers), walk through what happens when the dependency is absent or the ordering shifts at runtime.
- **The merged result, not the commit stack.** Review the final combined state of the PR — and re-check it against the current base tip if the branch is behind — rather than commit-by-commit. Individually sensible commits can compose into a contradiction.

### Test coverage is a review dimension

For each behavior change the PR introduces, name the test that exercises it — one that would fail on the base branch, passes on the PR, and asserts the **runtime effect**, not a proxy ("the generated string looks right" or "mirrors an existing pattern" verifies the shape or the sibling, not the behavior). A behavior change with no such test is a finding, even when the code looks obviously correct. If part of the path genuinely can't be tested, name the specific blocked sub-path — and confirm the adjacent runnable path is still exercised.

### Convergence

A pass that surfaced a substantive finding cannot be your last pass: one real find is evidence of unexplored ground, so sweep again until a pass turns up nothing substantive. The converse also holds — don't invent findings to fill a quota; a clean PR earns a short review.

### When an adversarial refutation pass is worth it

The verification above is the default and is usually enough. A heavier technique — challenging each candidate from an independent context (a separate reader per finding, told to *refute* it, and for a high-stakes blocker more than one from distinct angles: does it reproduce, is the mechanism right, does the named consumer actually break; refuted-but-unproven becomes a `question:`, not an `issue`) — pays for its cost only when a single reasoning context's blind spots would otherwise go uncaught. Reach for it when **two or more** of these hold, not by default:

- the finding is a **judgment call, not a mechanical fact** — "is this actually a race?", "does this design break the consumer's contract?" rather than "does `from + size` overflow?" A second context re-tracing a deterministic claim reaches the same answer, so independence adds nothing there; it earns its keep only where reasonable reviewers could differ. Every Step 2 approach objection meets this one by construction, so for those it takes just one of the others to make the pass worth running.
- you are reviewing **solo in one pass, without a fan-out of independent finders** — the independence a refutation pass buys is already present when several finders disagree and hedge their own confidence.
- the pass is **rushed or low-effort**, where the "verify before asserting" discipline is the thing most likely to be skipped — here the refutation raises the floor rather than the ceiling.
- the **cost of a false positive is high** — a blocking `issue` on a `--post` round, or a request-changes verdict, where a wrong call burns author trust.

When none of these hold — mechanically checkable findings, already fanned out, careful effort — the pass is redundant with the discipline above: it re-runs verification you already did and catches nothing new. It was tried as a mandatory always-on stage and reverted after a real-PR test showed exactly that, so keep it a conditional escalation, never a default step.

Verify thoroughly — but the evidence belongs *inside the finding it supports*, not in a standalone recap, and a cleared concern usually needs no words at all (see Step 4).

## Step 4 — Compose the review

The review's job is to surface what needs action. Reviewer and author attention is the scarce resource — PR review is a bottleneck, and every line that doesn't change what the author does is pure cost. Lead with action.

The body is **earned, not mandatory, and the default is none.** It exists only to carry what no single inline line can: a cross-cutting concern with no line to sit on, or a direct answer to a question the author asked on the PR. A Step 2 approach objection about the shape of the change rather than any one line is the other thing that can earn one — but anchor it wherever it can be anchored (on the function that shouldn't exist, or the call that should have gone through the existing hook), because a design essay in the body is easier to write and easier to skim past than the same point sitting on the line that shows it. **Summarizing or triaging the inline comments is not such a thing.** Each inline comment already states its own blocking-ness in its first line (the inline rules below require it), so a body that partitions them ("three block, three are optional") only re-derives what the comments already say. That is not a neutral convenience: it adds reading with no new information, which for an author already fatigued by comments is a net cost, and the "verdict + theme + what blocks" shape reads as bot output. A blocking/non-blocking tally therefore **never** earns a body. The only cross-finding note that does is genuinely synthetic: a dependency the per-comment text can't state ("land #2 before #1 or the fix won't apply"), or that several comments share one root cause so only that root need be fixed. The aggregate verdict is **not** by itself one of those things. A single blocking inline comment already conveys that the PR is not ready through its own wording, so a body that merely restates it or points back to it ("this isn't ready to merge; see the comment on X") is pure redundancy, and the author reads that announce-the-obvious sentence as bot output. A comment that says the change doesn't do what the ticket asks, or merges code nothing reaches, needs no cover note to declare that it blocks. So when one inline comment already carries the verdict, post the inline comments with an **empty body** (Step 5 shows how). Reach for a body only when the disposition genuinely is not derivable from the inline comments on their own. A multi-paragraph cover note that re-tells each finding is the loud failure mode; a one-line body re-announcing a verdict the inline comment already implies is the quiet one. Resist both, and keep the "if it would just be LGTM, post nothing" rule from Step 5.

When a body is warranted, its shape is:

1. Verdict first — **disposition + one headline reason + scope**, nothing else. Disposition is "merge", "merge after X", "needs work", or — when Step 2 left the approach unsettled and you deliberately held the detailed pass — "the direction needs agreeing first"; the headline is the single biggest reason (point at the finding numbers); scope is the bar you're judging against (e.g. "as a POC none block it; as production code they do"). **"Verdict first" means open with the call in your own words — not print a `Disposition:` / `Verdict:` / `Summary:` label in front of it. A literal label header is the same bot fingerprint as a stamped taxonomy tag (see the inline rules below): write "I think this is good to merge — nothing here blocks" or "This needs work first — …", never "Disposition: merge — …".** Don't tour the architecture or grade it ("the design is coherent", "the happy path is plausible") — that's narration-plus-praise the author can't act on. A maintainer scanning the PR should get the call and the one reason in a sentence or two.
2. Findings — but each lives in **exactly one place**. When you post inline (`--post` or `--stage`), the inline comment *is* the finding and carries its own evidence (its failure-mode sentence, or the verification that grounds it); the body must **not** restate it. Point to it with a *bare reference* — "the inline question on the `JacksonConfig` change" — never a one-line recap of what it says ("…that the shared mapper also reaches the scheduler"): the moment the clause explains the finding, it's a restatement in disguise. A body that re-narrates its inline comments is the same findings said twice — pure duplication, and the most common way the summary bloats. Only a finding with **no** inline home — a cross-cutting or PR-level concern — gets stated in the body itself.
3. End by making explicit what blocks merge — a short list when it's more than one thing, a single sentence when several findings share one blocker, and nothing when nothing blocks. (If the *only* body-worthy content would be a statement of what blocks — whether one blocker or several — there is no body at all: each inline comment already states its own block, per the default above.) Don't reach for a fixed boilerplate header: a verbatim string like "Needs action before merge:" stamped on every review is itself a bot fingerprint. Say what's left to do the way you'd say it to a colleague.

A "ready to merge" verdict with nothing left to act on is **not** something you post — see Step 5. It goes to the person who asked for the review, in conversation, not as a comment on the PR.

Evidence lives *inside the finding it supports*, not in a standalone "what I verified" section — a real finding is self-justifying once the reader checks it against the code, so a separate verification recap is redundant overhead. **Checked it and it's fine → say nothing.** Do not note cleared concerns "so they aren't re-raised": if the thing is trivially checkable, a later reviewer checks it as fast as you did and your note saves no round; if it isn't, a one-line reply when/if someone actually raises it costs less than pre-empting it on every review.

There is no exception — and on this the body is absolute: verified-clean material never appears in it, not as a section, a bullet, a terse line, or folded into prose. Even when cross-cutting verification was the whole point of the review (e.g. a pom.xml PR's "are the artifacts byte-identical?"), the result is reflected only in the verdict's disposition and the confidence behind it — never written out as a verified-clean note. If such a result genuinely must be on the record, it goes in a single inline `note (no action needed):` anchored to the relevant line, never in the body. On a **re-review** this bans the resolved-finding recap specifically: do not open with "all N points from last round are addressed" or otherwise tally what got fixed. When every prior finding is resolved and nothing new surfaced, there is nothing to post at all: tell the user it's ready to merge in the conversation (Step 5), rather than posting a review body that just announces "merge" — a bot-style "this is ready to merge / LGTM" comment is exactly what makes the author feel they're dealing with a machine instead of a person.

Rules for every inline comment, no exceptions (this is the part PR authors complained about when missing):

- Every inline comment must either request an action or ask a question, and its **first line must make clear what kind of comment it is and what (if anything) the author has to do**. Carry that the way a human reviewer would — in plain language ("This needs fixing before merge — …", "Optional: …", "Is this intended?") — rather than stamping every comment with a taxonomy tag. A column of `issue (blocking):` / `suggestion (non-blocking):` / `nit:` prefixes down the page is itself a bot fingerprint — **and so are the em-dash and colon variants (`Question — …`, `Non-blocking suggestion: …`, `Minor: …`): a label is a label whatever punctuation trails it, and "the first word names the category" is the tell. Open with the thing itself instead — the actual question ("Was this side effect intended?") or the actual ask ("Worth logging this rather than dropping it silently — …"). Casual vocabulary doesn't launder a label: `Naming trivia, take or leave: …` and `Tiny style thing: …` are the same stamp in softer clothes. The test for any opening phrase + colon is whether the phrase diagnoses the code or classifies the comment — `Leftover from the removed handler: X and Y are no longer used` survives because deleting the phrase loses the why; `Naming trivia:` deletes clean, so delete it and state the thing itself, letting any take-or-leave disposition trail the substance rather than front it. A pet opener recurring across comments or review rounds ("take or leave" in two consecutive rounds) turns even mild phrasing into a template.** Reach for an explicit label only when the prose doesn't already make the blocking-ness obvious, or when the maintainers have asked for those tags. Whichever form you use, these are the distinctions that must come through:
  - **blocking** — must be fixed before merge
  - **suggestion (non-blocking)** — recommended change the author may decline
  - **question** — a genuine question whose answer affects the verdict. Also use this for uncertainty about an observed side effect ("this changes X — intended?"); a question invites confirmation from people with more context far better than an FYI does.
  - **nit** — trivial, take or leave
  - **note (no action needed)** — exceptional. Allowed only when it does one of these jobs:
    1. records that a behavior change was seen and deliberately accepted, so the audit trail shows it wasn't missed if something breaks later; or
    2. warns a specific future reader at the line they will be looking at (e.g. whoever cuts the next release).
    If it does neither and isn't really a question in disguise, it's narration — don't post it anywhere.
- A blocking comment must contain a concrete failure-mode sentence: **"if merged as-is, X breaks because Y."** If you cannot write that sentence, it is not blocking — downgrade it or drop it. "Low risk" without naming the risk, "matches the existing pattern", "probably fine" are dodges, not verdicts: name what breaks, who notices, and how.
- Silent-failure upgrade: when the failure mode produces wrong behavior without throwing (a swapped repo id, a dropped field, a silently replaced MockMaker), treat it one level more seriously than a crash — CI cannot catch what doesn't throw, so the cost of discovery lands on users.
- When presenting alternatives, always state the recommended default. Never end on "either option is defensible" without picking one.
- Do not narrate what the diff does — the author wrote it.
- Keep each inline comment to its finding and the fix — don't repeat the same cross-cutting point across comments. Verified-clean cross-cutting verification does NOT get relocated to the body (see Step 4 — the body carries none); at most it is a single inline `note (no action needed):`.
- Use GitHub ```suggestion blocks when the fix is a concrete replacement of added lines (RIGHT side only — suggestions cannot attach to deleted lines).
- Scale to the requested effort: by default, fewer high-confidence findings. At high effort, widen the sweep and surface uncertain findings too — explicitly as `question:`, never as unverified `issue`s.
- Fewer, sharper comments beat exhaustive ones.

## Step 5 — Post or stage (only with consent)

Posting publishes under the user's own GitHub account. Post only when the user passed `--post` or explicitly asked; stage only when they passed `--stage` or asked for a draft or to stage; with neither, present the full review in the conversation and offer to post (or stage). `--stage` sits between conversation-only and `--post`: the review is created on GitHub in PENDING state — invisible to the author, no notification fires — and the user finishes it in the UI: edits wording, deletes comments, then submits or discards. Staging is a checkpoint, not a lower bar — the user may submit the staged comments unedited, so a staged review must already pass every rule in this file, including the gate below.

**A clean "ready to merge" verdict is reported to the user here, never posted to the PR.** When the review turns up nothing to act on — fresh PR or re-review where every prior finding is resolved — there is no review to publish or stage: tell the user it's ready to merge in the conversation and stop. Do not open a review (even with `--post` or `--stage`) whose body just announces the PR is good to go. Posting "this is ready to merge / LGTM / all looks good now" is the clearest tell that a bot, not a person, is on the other end, and it's the thing PR authors most dislike. Posting still happens normally when there ARE action items — you post those findings; you just never add a standalone merge-readiness flourish.

**Pre-posting gate** — before presenting, staging, or posting, write these five as five explicit, standalone lines in your report to the user — verbatim, not paraphrased, not woven into prose narration. If any cannot be said truthfully, go back and fix the review first:

> "I identified the problem this PR is meant to solve — linked issue, tracker ticket, or description — and checked that the change actually resolves it; where I couldn't reach the ticket, I said so, and where the description states the PR's own guarantees I tested them one at a time instead of taking them as given. I went past 'it works' to whether it is the best fix available, naming the alternatives a maintainer of this codebase would have weighed. Any approach objection I raise names both a concrete alternative and the concrete cost of the approach taken — maintenance cost counts, 'this feels hacky' does not — and where I would merely have done it differently, I wrote nothing. I accounted for every hunk as required by the ticket or not, and asked for the removal of what was not, including changes I had verified to be harmless."

> "Every finding was verified by [building / running / tracing / upstream check], not just read off the diff."

> "Neither the summary verdict nor any inline comment's first line leads with a stamped label — not `issue:` / `suggestion:` / `nit:`, not the em-dash/colon variants (`Disposition: merge`, `Question — …`, `Non-blocking suggestion: …`), and not their casually-worded cousins (`Naming trivia, take or leave: …`, `Tiny style thing: …`); each says in plain language what it is and what the author must do, and either requests an action or asks a question. Every blocking comment contains its failure-mode sentence; and no comment — fresh or threaded reply — exists merely to acknowledge a fix or credit resolved work."

> "The summary body carries only what no inline line can, and when a single inline comment already conveys the verdict it is empty. I did not add a body to announce a disposition the inline comments already imply: a lone blocking comment whose wording shows the PR is not ready needs no cover note. A body appears only for an unanchored cross-cutting concern, the author's question, or a genuinely synthetic cross-finding note (a fix-ordering dependency, or a shared root cause); it never merely summarizes or tallies the blocking-ness that each inline comment already states, and even when present it never restates a finding (a pointer is a bare reference, not a one-line recap of what the comment says; a body paragraph reproducing an inline comment is the finding said twice). Zero verified-clean or cleared-concern content anywhere in it: no 'what I checked' line, bullet, section, or aside, and none folded into prose; and on a re-review, no 'prior points addressed' recap, since a resolved finding earns silence, not a tally. The verification I did shows up only as the confidence behind the verdict, never written out; if a result must be on the record it is a single inline `note`, not body text."

> "Needs action before merge: [list, or 'none' — and if 'none', this verdict is reported to the user here, not posted to the PR nor staged]."

Mechanics that are easy to get wrong:

- Submit one review: `gh api repos/<owner>/<repo>/pulls/<n>/reviews --input payload.json` with `"event": "COMMENT"` (posted rounds only — a staged round omits `event`, two bullets down; never APPROVE or REQUEST_CHANGES unless the user explicitly chose that), a `body`, and a `comments` array.
- Before **any** review create, posted or staged: re-run the Step 1 pending-review check. A user gets one pending review per PR — either kind of create 422s "User can only have one pending review per pull request" against it, and REST cannot append to an existing one. On a hit (the pre-check, or that 422 — one can appear between Step 1 and now), stop and ask rather than touching it.
- Re-run the Step 1 **conversation** fetch at the same moment, not just the pending-review check — `gh api repos/<owner>/<repo>/pulls/<n>/comments --paginate` and `gh pr view <n> --json reviews,comments`. Step 1 is however long your verification took (often an hour) behind you, and a comment posted in that window can duplicate a finding you are about to make, answer it, or **clear** it — a maintainer writing "if you do this, then also do X" has accepted the thing you were about to block on, and posting over them is worse than a plain duplicate because it contradicts the person whose call it is. Diff the new material against every finding in your composed review and drop, downgrade, or re-anchor whatever it already covers, exactly as Step 1 requires for a prior round. If the new material is substantial enough to change the verdict, go back to Step 2 rather than posting what you had.
- Staging: same payload but **omit `event` entirely** — GitHub creates the review in PENDING state ("you will need to submit the pull request review when you are ready").
- Staged thread replies: the `/replies` endpoint below publishes immediately and cannot stage. Attach the reply to the pending review via GraphQL instead: `addPullRequestReviewThreadReply` with `pullRequestReviewId` (the pending review's `node_id`, returned by the create call), `pullRequestReviewThreadId`, and `body`. Find the thread id in the PR's `reviewThreads` connection by matching the target comment's REST id against `fullDatabaseId` (github.com's schema no longer exposes `databaseId` on review comments — older GHES schemas are the reverse, so if `fullDatabaseId` errors as an unknown field, match `databaseId` instead; `fullDatabaseId` comes back as a **string**, so a numeric jq comparison silently matches nothing). For a replies-only round, create the pending review first with no comments so there is something to attach to — an empty `{}` payload suffices.
- Verifying a staged review: pending comments do **not** appear in `/pulls/<n>/comments` — list them with `gh api repos/<owner>/<repo>/pulls/<n>/reviews/<review_id>/comments --paginate` instead. The expected set is everything the composed review contains — the payload's comments **plus every thread reply it called for (attached via GraphQL)**; match replies by `body` and `in_reply_to_id` — they are not duplicates to clean up. Compare by `{path, body}`, not `{path, line}`: until the review is submitted, pending comments report `line` and `side` as `null` (only the diff-relative `position` is populated), so a line-based diff false-mismatches on every staged comment. If something looks missing, re-query after a few seconds before repairing — reads lag writes here too. If the staged set is genuinely wrong, repair per the fixing bullet below (a missing reply attaches in place; anything else is delete-and-restage) — never per-comment DELETE, which would silently eat your own drafts.
- Hand-off for a staged review: end the report with the review URL and say plainly that it is visible only to the user until they submit it (Files changed → "Finish your review"), and that a forgotten pending review is a review that never happened. Discard from the CLI is `gh api -X DELETE repos/<owner>/<repo>/pulls/<n>/reviews/<review_id>` (pending reviews only). Which event to submit with — comment, approve, request changes — is the user's call to make in the UI, not something to instruct.
- Build `payload.json` with `python3` + `json.dump` — raw tabs/newlines in hand-written JSON break the API call.
- Anchoring: `"side": "LEFT"` with line numbers from the **merge-base version** of the file for deleted lines; `"side": "RIGHT"` with line numbers from the **PR-head version** for added/context lines. Get exact numbers via `git show <ref>:<path> | cat -n`. Confirm the merge-base first (`git merge-base origin/<base> pr-<n>`); if it equals the base tip, base-branch line numbers are safe for LEFT.
- Multi-line comments use `start_line`/`start_side` plus `line`/`side`, and the whole span must fall inside a single diff hunk.
- Comments appear under the user's name — write them in first person, collegial tone.
- Threaded replies (Step 1 may send you here to build on an existing thread instead of posting fresh): `gh api repos/<owner>/<repo>/pulls/<n>/comments/<comment_id>/replies -f body=...`. These post as **standalone** review comments — they won't appear in any review payload's `comments` array and carry their own ids, so don't expect them in the main-review verification below. With `--stage` this endpoint is wrong — it publishes instantly; use the staged-thread-replies path above.
- Verify after posting — but **trust content, not counts**: `gh api repos/<owner>/<repo>/pulls/<n>/comments --paginate --jq '.[] | select(.pull_request_review_id == <id>) | {path, line, side, body}'`. The `--paginate` is mandatory: `gh api` returns 30 comments per page, and a busy PR (a prior round + replies) easily exceeds that, so without it the query gives **false negatives**. Reads can also lag a few seconds behind the write. Diff what comes back against what you submitted by `{path, line}`; if something looks missing, re-query (allowing for lag) and inspect — **never re-post on a mismatch**, that is exactly how duplicate comments get created. If duplicates already exist, delete the extras with `gh api -X DELETE repos/<owner>/<repo>/pulls/comments/<comment_id>`. Then report the review URL.
- Fixing a review after posting: edit in place, never post a second review. Update the body with `gh api -X PUT repos/<owner>/<repo>/pulls/<n>/reviews/<id> --input body.json` (a `{"body": "..."}` file); `{"body": ""}` is accepted and blanks the body outright, which is the right move when you realize the body only re-announced what an inline comment already said. Edit inline comment wording with `gh api -X PATCH repos/<owner>/<repo>/pulls/comments/<comment_id> -f body=...`. Editing leaves no duplicate-review or duplicate-comment churn. A staged review needs none of this — the user edits pending comments directly in the UI; if the staged set itself is broken, the repair depends on the break: a missing or newly requested thread reply attaches in place via the staged-thread-replies path (the pending review's `node_id` is in the reviews listing), no restage needed; anything else (bad anchors, a missing top-level comment) is delete-and-restage, and the rebuild source depends on when. Before hand-off no user edit can exist: rebuild from your composition with the defect fixed. After hand-off, list the current drafts first (`.../reviews/<review_id>/comments --paginate`) — on wording and deletions the drafts win (restaging your original would silently revert the user's UI edits, and your reverted text then publishes when they submit trusting changes no longer there), while the piece the repair exists to restore (the missing comment or reply, the corrected anchor) comes from your composition, the only place it exists. Deletion evaporates the GraphQL-attached replies along with everything else, so restage the replies too, then re-verify against the corrected set you just rebuilt — never against a rebuild that inherited the loss, which would certify the very gap you came to repair.

## Anti-patterns

- **Don't invent concerns to look thorough.** Review depth should track risk; a clean PR gets a short, confident review. Diminishing returns are a real signal, not a failure.
- **Don't post unverified suspicion as an `issue`.** If you couldn't verify it, it's a `question:` — or more homework for you, not the author.
- **Don't critique an inflated version of the PR.** When disagreeing with an approach, respond to the author's actual scope; larger redesigns are follow-up `suggestion`s, not blockers on this PR. That is not licence to wave through an approach that doesn't solve the problem — Step 2 draws the line: what you hold back is the redesign that would deliver *more*, never the objection that this delivers the *wrong thing*.
- **Don't mistake a verified diff for a solved problem, or a solved problem for a well-solved one.** A review can verify every changed line and still miss that the change doesn't fix the reported bug — and it can confirm the bug is fixed while missing that it was fixed by parsing a display name, sleeping for two seconds, or suppressing the check that was complaining. "The tests pass" is silent on all of it, by construction. Line-level rigour is the easy half and the one attention drifts to by default, because it's mechanical and always has something to say. The other half is where the review earns its keep: the author cannot do it for themselves, having already concluded the approach is right.
- **Don't let severity labels substitute for analysis.** A finding is blocking because of its written failure mode, not because it pattern-matches "correctness". Small-looking code patterns (an unclosed resource, a swapped identifier) are routinely under-labeled.
- **Don't restore confidence the author already has.** A PR author shipped because they believe the change is right; a recap of what they got right is cost without benefit. The review's value is the delta — what must change, plus the rare verified-clean item a later reviewer would re-raise. Passing CI is not a reason to soften the action items: both the expensive bugs and the bottleneck live in what the tests already wave through.
- **Don't acknowledge fixes (especially on re-review).** A human re-reviewer comments only on what's still wrong — they don't reply "thanks, that's resolved" to every thread the author closed, and they don't open the body tallying what got addressed. Fixed and no remaining problem → no comment; the disposition flip to "merge" is the acknowledgment. Writing the confirmation out feels polite, but it reads as slop and buries the one comment that does still need action. This is the gap authors notice most: the re-review that should have been two lines turns into a wall of "looks good now."
- **Don't let the review read as machine output.** The content rules above are about substance; the *form* matters too, because authors disengage the moment a review smells automated. Three habits give it away even when every finding is sound: a rigid recurring template (a `Disposition:` / `Verdict:` header → numbered findings → a verbatim "Needs action before merge:" footer on every PR); a taxonomy tag stamped on the front of every comment (including its em-dash/colon variants like `Question — …` or `Non-blocking suggestion: …`, and their casual cousins like `Naming trivia: …`); and a comment that opens by announcing its own speech act (`A correction to my earlier rationale: …`, `One observation: …`) instead of leading with the substance — when retracting something you claimed in an earlier round, open with the corrected fact and let the retraction trail it ("It turns out X, so part of my reasoning above was wrong"), never with the announcement. Write the way a careful human colleague writes — vary the structure to fit the PR, let prose carry blocking-ness, and never post a standalone "ready to merge / LGTM" comment; that verdict goes to the person who asked, in conversation. A subtler tell lives in the prose itself: a heavy run of em-dashes (the `—` character now reads as a strong "written by a model" signal) and uniformly polished, balanced sentences. In the posted review, prefer commas, periods, and parentheses over em-dashes, and let the phrasing be a touch plainer than a machine would buff it. The goal is a review the author reads as coming from a person who actually looked, not a form a tool filled in.
- **Don't fake confidence on a PR too large to review.** When a PR is too big or sprawling to review with real confidence as one unit, say so plainly and suggest splitting it (by concern, or behavior-change vs. mechanical churn) rather than producing a sweep that reads as thorough but can't be. A reviewer's honest "this exceeds what I can verify in one pass — here's how I'd split it" is worth more than five findings that miss the sixth. Name what you *did* verify and what you couldn't reach.

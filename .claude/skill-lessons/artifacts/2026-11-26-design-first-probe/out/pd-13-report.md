**What I checked this turn**
- **A's anchor and the expiry path.** Line 2467 of `StockManagementServiceImpl` is the `groupingBy(p -> Pair.of(...))` line. The expiry job groups the same way (`StockBatchExpiryJob.java:128-130`), keeps that order when it lists the map's entries (`:163`), and alerts only the first 4 (`:173`, `:183-213`). A batch that has been notified is never selected again (`StockManagementDao.java:1607`, the `expiryNotificationDate is null` filter). I worked out the hashes by hand for one store with items 1 to 5:
  - master puts them in the map as 1,2,3,4,5 (hashes 32 to 36);
  - the head puts them in as 1,3,2,5,4 (hashes 0,3,2,5,4);
  - so the 4th alert goes to item 5's batch instead of item 4's.
- **B's anchor and claim.** Line 3228 is the `isValidEmail` return line. The pattern ends `[a-zA-Z]{2,7}$` and `matches()` must use up the whole input, so an address ending in a dot can never match. The same guard was on master (`utils/StringUtils.java`), so the PR moved it unchanged.
- **S1.** All 10 call sites (not 9) match master's 10 `NumberFormatUtil.qtyDisplayFormat` calls one for one, and each uses `ModuleConstants.QUANTITY_FORMAT`, which is the same pattern string. Greptile raised the test gap in an earlier thread, the author answered, and the maintainer approved after that.
- **S3.** I ran master's pre-#76 regex (without possessive quantifiers) on the new 50,000-repetition local part and it throws `StackOverflowError`. As a control, the possessive pattern on the same input returns `true`. So the smaller test still guards against the overflow.
- **S8.** Nothing in `api/src/main` or `omod/src/main` calls `Locale.setDefault`. As a control, the same search finds 6 calls in the test tree. I couldn't check openmrs-core, because its sources aren't in the local Maven repository.

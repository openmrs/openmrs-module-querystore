**Draft A, reworded.** What triggered the rewording is S5's report (ac3): "That changes which 4 expiry alerts each user gets". Both draft A and S5 come from one cause, the hash change in `Pair`, so they become one question on `StockManagementServiceImpl.java:2467`:

> Does anything rely on the order of maps keyed on `Pair`? Commons `Pair` hashes as `left ^ right`, not `31 * left + right`, so with items 1 to 10 at party 3, `total` comes back 3,2,1,7,… instead of 3,4,…,10,1,2, and with one expiring batch each, `StockBatchExpiryJob`'s four alerts go to items 3,2,1,7 instead of 3,4,5,6. The ticket asks for no behaviour changes.

- **Expiry alerts:** the alert loop takes the first 4 entries of the `partyStockItemMap` hash map in iteration order (`StockBatchExpiryJob.java:173-213`). A batch that has been notified is never selected again (`StockManagementDao.java:1751`).
- **The orders quoted:** I worked out both bucket orders by hand for keys (3,1)…(3,10), and they match A's verified run.
- **Why a question:** the old order was arbitrary too, so the ticket author should decide whether this counts as a behaviour change.

**Draft B, as drafted.**
- **The check never changes the result:** I ran the head's email pattern on its own, with and without the `endsWith(".")` check. Inputs ending in a dot, up to 200,000 characters, always gave `false` with no stack overflow, even at `-Xss256k`. As controls, `user@example.com` matched, and master's old non-possessive pattern overflowed the stack on the same inputs.
- **The suggested line:** running `spotless:apply` leaves it unchanged. As a control, the formatter rewrote a deliberately misformatted copy into exactly this line.
- The working copy is clean again.

**Set aside:**
- **S1:** Greptile already raised this, and the author replied in that thread. The part that still holds is that a call site could use the wrong pattern. All 10 quantity sites (not 9) map `qtyDisplayFormat` to `QUANTITY_FORMAT` one for one, and the integer sites map to `INTEGER_FORMAT`.
- **S2:** `ModuleConstants.QUANTITY_FORMAT` already gives the pattern a single source. Adding a helper back would work against the ticket's aim of removing `NumberFormatUtil`.
- **S3:** the existing tests (`StockManagementServiceTest`, `StockOperationDTOValidatorTest`) also sit in the root package. 50,000 `.a` repetitions still overflow the stack under master's old pattern, so the long-address test still catches that regression.
- **S4:** the author rebased, so the commit history can't show when the tests were written. What the claim stands for (same patterns, same regex) I checked directly against master.
- **S6:** each `BiConsumer` import replaces the `Action2` import on the same line, which is the smallest diff possible. Converting to lambdas would add changes the ticket doesn't need.
- **S7:** this happens with any deleted class in any Maven build, not because of this PR. CI and releases build with `clean`.
- **S8:** the output only differs if something calls `Locale.setDefault` while the server runs. Even then, master captured the locale at whatever moment the helper class first loaded, which was arbitrary too.

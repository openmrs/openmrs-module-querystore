## The two comments

**A, reworded and moved to `StockBatchExpiryJob.java:130`.** Two things made me change it. First, it names a field `total`, but the field is `totals` (`StockInventoryResult.java:16`). Second, the ac3 agent found that the same change decides "which 4 expiry alerts each user gets", which is a stronger case than the REST order. I reproduced the order change with master's `Pair` source and the real commons-lang3 3.18.0 jar. A single item gives the same order on both. With one store and 5 items, master alerts on items 1, 2, 3, 4 and the head on 1, 3, 2, 5. Draft A's 10-item example also reproduces exactly.

The persistence claim holds only partly, so it stays out of the comment. Alerted batches get `expiryNotificationDate` (`:212`, then `:141`), and the DAO skips them from then on (`StockManagementDao.java:1751`). With SMTP set up, the email also marks the other batches as notified (`:396`), so a batch outside the first 4 never gets an alert. Without SMTP it gets one on a later run.

It's a question rather than a blocker because both orders are arbitrary hash orders and nothing is wrong in either. The comment as it goes out (about 58 words):

> Was it intended that the expiry job now picks a different 4 alerts per user? Commons `Pair` hashes as `left ^ right`, not `31 * left + right`, so this map iterates in a new order: with one store and expiring items 1 to 5, master alerts on items 1 to 4, this branch on 1, 2, 3 and 5. `totals` for `totalBy=LocationStockItem` reorders likewise.

## Set aside
- **S1:** Greptile's thread on this test was answered by moving the pattern into `ModuleConstants`. What's left is a call site that doesn't use the constant, and there is none: all 10 sites pass `ModuleConstants.QUANTITY_FORMAT` (grep). Testing them would take context-sensitive tests of two scheduler jobs, which this refactor ticket doesn't ask for.
- **S2:** The pattern is defined once, so nothing can drift. The ticket says to remove `NumberFormatUtil` where it adds nothing, so a new helper would bring back what it removes.
- **S3:** The root package already holds `StockManagementServiceTest` and `StockOperationDTOValidatorTest`. 50,000 repetitions still overflow the stack with the pattern from before #76, and so does 100,000, so the test still catches that regression. The class name is a matter of taste.
- **S4:** Every pinned number and email example gives the same result on master's own `NumberFormatUtil` and `StringUtils`. A deliberately wrong control row flagged a difference. So what the description claims is true, and the commit order goes away in a squash merge.
- **S6:** The new import sits where master's `Action2` import already sat out of order, which keeps the diff minimal. The formatter has no import-order rule, and switching to lambdas would be churn beyond the ticket.
- **S7:** This applies to any PR that deletes a class, not to this change. It's an unconfirmed lead, and no published artifact is shown to carry the old classes.
- **S8:** Nothing in production changes the default locale. The module's main code has no `Locale.setDefault`, and neither do OpenMRS 2.8.0's api or web jars (a `javap` search that found the call in my control class). Master's static instances were also created only on first use.

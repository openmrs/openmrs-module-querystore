## The ticket, O3-6316 (in full)

Summary: Stock Management: Stock source service

Why: One service and one data access class hold the whole module, which makes every change risky and hard to review. Stock sources are the smallest area, so they set the pattern the other areas follow.

Description: Give stock sources their own service and data access classes, following standard OpenMRS conventions.

Details:
* Follow the standard OpenMRS shape: a service interface, its implementation, and a data access interface with a Hibernate implementation.
* Queries return entities, not DTOs.
* A small search object replaces the existing search filter classes for this area.
* Today the single service has 147 methods and the data access class is over 5,000 lines.
* Agree the package layout and naming here, since the other seven areas copy it.

Implementation notes:
* Classes: StockSourceService, StockSourceServiceImpl, StockSourceDAO, HibernateStockSourceDAO and a StockSourceSearch object.
* Register the service in moduleApplicationContext.xml the same way the existing service is registered.
* Move the four stock source methods (get by uuid, search, save, void) and their queries out of the old service and data access class.
* Billing's CashPointService and its DAO are a good model for the shape.
* Point the stock source REST resource and any other callers at the new service.

Acceptance criteria:
* Stock sources are handled by their own service and data access classes.
* Every service method declares the privilege it requires.
* Nothing else in the module calls the old stock management service for this area.
* Existing behaviour is unchanged and covered by tests.
* The structure is documented as the pattern for the remaining areas.

   - Created `StockSourceService` (interface) and `StockSourceServiceImpl` (implementation) following OpenMRS Billing module   conventions.
   - Created `StockSourceDAO` (interface) and `HibernateStockSourceDAO` (Hibernate implementation).
   - Created lightweight `StockSourceSearch` criteria object and removed obsolete `StockSourceSearchFilter`.
   - Wired `HibernateStockSourceDAO` and transaction-proxied `StockSourceService` in `moduleApplicationContext.xml` and registered in `serviceContext`.

   - Moved the 4 stock source methods (`getStockSourceByUuid`, `findStockSources`, `saveStockSource`, `voidStockSources`) and their queries out of `StockManagementService` and `StockManagementDao`.
   - Reduced `StockManagementService` method count from 147 to 143.

3. Security Privileges:
   - Explicitly annotated every method in `StockSourceService` with appropriate `@Authorized` privileges:

     - `Privileges.TASK_STOCKMANAGEMENT_STOCKSOURCES_MUTATE` for save/void/purge operations.

4. Caller Redirection:
   - Updated `StockSourceResource` (REST API) to delegate directly to `StockSourceService`.
   - Updated internal callers (`StockItemReferenceResource`, `StockItemImportJob`, `StockOperationLineItemReport`, `BatchJobValidator`) to use `StockSourceService`.

5. Test Coverage:
   - Added `StockSourceServiceTest` covering CRUD, voiding, purging, and search criteria.
   - Added `StockSourceDAOTest` covering Hibernate criteria and persistence.
   - Added `StockSourceResourceTest` verifying REST endpoints.
   - All 29 module tests pass with 0 failures (`BUILD SUCCESS`).

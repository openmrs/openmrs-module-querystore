Decision: I'm filing four items as questions (R1, R3, R7, plus R1's own criterion) and setting aside six. Filed: R1, R3 and R7. Set aside: R2, R4, R5, R6, R8 and R9.

**Filed**
- **R1 (question):** The method says a missed acceptance criterion is always raised. Where the ticket's purpose looks met, it goes in as a question. That's the case here. `ModuleConstants.java:68-131` now holds a logger and six `public static` helpers, so the head misses "No static settings utility remains" as written. But the ticket's reasons for that criterion are dealt with: the name clash is gone, the helpers log, and they only keep rules core doesn't have.
- **R3 (question):** Master read each of these settings through one getter. The head copies them instead:
  - The page-size read, with `1000` twice, is pasted into 7 reports. All of them extend `ReportGenerator`.
  - The pack-size read is pasted 5 times in the service (lines 1642, 1737, 2106, 2382, 2500).
  - The ticket offers "one place per setting" as a choice. Finding A already shows a changed copy goes unnoticed by the tests.
  - It's a question rather than a suggestion: the method says a proposed alternative must go past a blind reader before it's posted, and I can't start one here.
- **R7 (question):** Lines 2907-2908 sit inside the hunk the PR rewrote at 2905-2906. An invalid email setting is dropped without a log. If the role setting is blank, the INFO line then wrongly says the settings are "not set". This is the same kind of problem as B, and the ticket asks for unparseable settings to be logged. It predates the PR, so it's not blocking, and it's a question for the same no-blind-reader reason as R3.

**Set aside**
- **R2:** Core 2.8.0 gives "Get Global Properties" to the `Authenticated` role (in core's bundled `liquibase-core-data-2.*.xml`). `UserContext.hasPrivilege` checks that role for every logged-in user. So only a site that took the privilege away hits the new exception, and on master such a site's settings were quietly replaced by defaults. Removing that kind of silent fallback is what the ticket asks for.
- **R4:** `getGlobalPropertyValue(key, "")` is the call the ticket prescribes, and it returns the same results as `getGlobalProperty(key, "")`.
- **R5:** Master has the same mismatch (`GlobalProperties` returned 100 and 1440; `config.xml` says 1000 and 10080). Fixing it would change a current default, which the ticket's third criterion forbids.
- **R6:** None of the three settings replaces the value the admin typed; each uses it as given. There's no exception being swallowed, and adding ranges would be new rules outside the ticket.
- **R8:** The message is core's, and core logs it with the exception. The stack trace includes the module's own calling line, so the setting can be identified. Any change belongs in core.
- **R9:** The moved line sits inside the import hunk the PR needs anyway for `ModuleConstants`. It adds no hunk and puts the import in sorted order. Spotless here runs only the Eclipse formatter, so the move isn't the formatter's work, but it costs no extra review.

The working copy is clean (`git status --porcelain` printed nothing), and the temporary folders I unpacked core's jar into are deleted.

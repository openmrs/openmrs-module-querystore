The reviewer was right to set aside six of the nine items (R1, R2, R4, R5, R6, R8) and wrong on three (R3, R7, R9). The working tree is clean and no build was run.

**Upheld**
- **R1:** Master's `GlobalProperties.java` read each setting with `getGlobalProperty`, caught every exception and returned a default. The head's six helpers in `ModuleConstants.java:71-131` only take a value that has already been read. They log the key and the bad value, and they keep master's rules exactly: true/yes/1 for the job switches, blank means true for pack size, `Math.max` with 1, 0 and 1440, and `<=0` falls back to 1000 or 30.5. None of the ticket's "Why" objections apply to them: they swallow nothing, there's no name clash, and core has no equivalent rules. The method says to treat the ticket as evidence and judge against the underlying problem, and that problem is solved.
- **R2:** Core 2.8.0 grants `Get Global Properties` to the Authenticated role in every core-data snapshot I checked (2.1.x to 2.7.x). Upgraded databases get it too: the 2.0.x update gives it to every role that had `View Global Properties`, and Authenticated has that in the 1.9.x data. Failing loudly here matches "No setting read swallows an exception silently".
- **R4:** With a `""` default, `getGlobalPropertyValue(key, "")` and `getGlobalProperty(key, "")` return the same thing and neither logs. With no cost to name, the method calls this taste.
- **R5:** The mismatches are real (`config.xml` says 1000 and 10080, the code says 100 and 1440) and are the same on master. The ticket's "Each setting keeps its current default" would forbid changing them in this PR anyway.
- **R6:** These values parse correctly and are used as entered. Nothing is swallowed and the code doesn't override them, so adding bounds would be new behaviour outside the ticket.
- **R8:** The disassembled `AdministrationServiceImpl` in core 2.8.0 builds the message "Unable to turn value '…' into type …" with no key. That is core's text, and the ticket requires reading through core.

**Rejected**
- **R3:** The ticket's wording does allow defaults at the call site. But master stated each default once, in its getter, and the head copies the page-size default 12 times across 6 reports, 30.5 six times, and the pack-size read 5 times. The method names duplicated logic as a wrong-shape signal. The reviewer's own finding A shows no test catches a changed call-site default, so these copies can drift apart without any test failing. That cost is concrete, and a "the ticket allows it" reason doesn't override it.
- **R7:** The method's "same defect, where the PR didn't look" rule tells the reviewer to check code the PR left alone, so "the PR doesn't rewrite this line" is not a reason. An invalid email is a setting value that is silently ignored, which the ticket asks to be logged. The INFO line that follows then says the settings are "not set", which is wrong. The reviewer raised the identical master-era boolean case as finding B.
- **R9:** Master already imported `Context`; the PR only needed to add the `ModuleConstants` import. The build's formatter (Spotless with the Eclipse formatter, from the parent POM 2.3.0) doesn't reorder imports, so the move wasn't required. The reason given is false, and the method's "does it do only that?" rule treats changes the ticket doesn't need as something to raise.

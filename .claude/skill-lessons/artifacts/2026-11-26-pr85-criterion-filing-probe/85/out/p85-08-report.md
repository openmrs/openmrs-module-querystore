I'm filing three of the nine and setting six aside. R2 is a question, and R3 and R7 are suggestions. R1, R4, R5, R6, R8 and R9 are set aside. The working copy is clean (`git status --porcelain` printed nothing), and I didn't build anything.

**Filed**
- **R2, question, on `StockManagementServiceImpl.java:2105`.** I checked this against core 2.8.0's compiled class. Core's `AdministrationService` requires the "Get Global Properties" privilege on `getGlobalProperty(String)`, `getGlobalProperty(String, String)` and `getGlobalPropertyValue(String, T)`. On master, every getter in `GlobalProperties` wrapped its read in `catch (Exception exception) {}`, so a missing privilege quietly fell back to the default. The c3 agent ran the same dispense request on both refs. Master got past the read; head failed with `APIAuthenticationException`. I can't name a shipped role that lacks this privilege: nothing in the module mentions it, and checking real deployments' roles needs access I don't have. So under the method it goes in as a question about a side effect, not a blocker.
- **R3, suggestion, on `DispensingLogsReport.java:56`.** All six reports that read the page size extend `ReportGenerator` (`StockConsumptionReport` through `StockItemInventoryReport`). Each one copies `positiveValue(KEY, getGlobalPropertyValue(KEY, 1000), 1000)`. Master had a single getter for it. The ticket's other option, "in one place per setting", can be met with an instance method on the base class, which is not a static utility. The cost is concrete: changing the default takes 12 edits, and finding A shows no test would notice a missed copy.
- **R7, suggestion, on `StockManagementServiceImpl.java:2907`.** These lines are context inside a hunk the PR changes, so the comment can sit there. An address that fails `isValidEmail` becomes `null` with nothing logged. If the role setting is also blank, the INFO line then says "Email and role notification settings not set", which is wrong. That is the ticket's own "mistyped setting fails silently" case. Master does the same, so it stays a suggestion.

**Set aside**

Core has none of those rules, so every shape that keeps them is either a helper or a copy at each call site. The six helpers do log, which answers each objection in the ticket's "Why" section.
- **R4:** For a `""` default, `getGlobalPropertyValue` and `getGlobalProperty` return the same thing, so the change would be cosmetic.
- **R5 and R6:** Master behaves the same, and the values in question are parseable. Changing them would break the criterion "Each setting keeps its current default".
- **R8:** The message "Unable to turn value '…' into type" lives in core's `AdministrationServiceImpl`, not in this PR. Core logs it with the stack trace, which shows the module call site.

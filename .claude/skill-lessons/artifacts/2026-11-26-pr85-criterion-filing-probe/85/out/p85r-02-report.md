**Five of the reasons hold (R1, R2, R4, R5, R6, R8 — six) and three don't (R3, R7, R9).**

**Upheld**
- **R1:** The ticket's Why describes the utility as "22 static methods that read the module's settings". The six helpers read nothing: every read is a core call at the call site, and `ModuleConstants` makes no `getAdministrationService` call. The helpers log bad values, and they keep master's rules: I re-read master's getters, and c3's 969 stored-value comparisons all matched. Moving them elsewhere has no cost the method could name, and the PR description already says where they live.
- **R2:** This is true at this head:
  - Core's data (`liquibase-core-data-2.7.x.xml`) grants Get Global Properties to Authenticated, which `UserContext` loads for every logged-in user. Anonymous has no privileges.
  - The one anonymous caller in the module is `StockOperationNotificationTask`. It runs on a new thread after `openSession()` and adds proxy privileges, but not this one.
  - On master that thread swallowed the exception, got null and logged a false INFO "settings not set". On head the same failure is logged at ERROR. Neither sends the notification.
- **R4:** For a `String` default, core's `getGlobalPropertyValue` returns the default on empty and otherwise builds `new String(value)`. That behaves the same as `getGlobalProperty(key, "")`, so the only cost is style.
- **R5:** `config.xml` has 1000 and 10080 and the code on master has 100 and 1440. The criterion "each setting keeps its current default" forbids reconciling them in this PR.
- **R6:** Master had no bounds on these three settings, and these values parse without any exception. Adding bounds would be new behaviour beyond the ticket.
- **R8:** In core 2.8.0 the message is built as `"Unable to turn value '" + value + "' into type " + class` and logged with the exception, so the stack trace shows which call site failed. The ticket prescribes core's method, so a better message is core's fix to make.

**Rejected**
- **R3:** On master each default lived in one getter. Head pastes the page-size rule and default into 7 reports (14 copies of `1000`), puts `30.5` in 7 places and pastes the pack-size read 5 times. The ticket also offers "in one place per setting". The method counts duplicated logic as a wrong-shape signal, and "working is the floor". The reviewer's own finding A shows no test would catch a copy that drifts. So this has a concrete alternative and a concrete cost, which makes it a non-blocking suggestion; "the ticket allows it" doesn't answer that.
- **R7:** "Not a line the PR rewrites" is not a test the method uses: it says to trace outward and treats the same defect left on the PR's path as a suggestion. This is the Why's own case, a malformed setting failing silently, two lines below a read the PR rewrote. The reviewer raised finding B on the same "master does the same" grounds. One caveat: in the only production caller, the task thread above, the read now throws before this line runs.
- **R9:** The reason is false:
  - `Context` was already imported on master.
  - `GlobalProperties` came in through `utils.*`, so no import had to be removed. The only edit the PR needed was adding `ModuleConstants`.
  - I ran `spotless:apply` offline on a scratch worktree with the import back where master had it. Spotless fixed an indentation I had broken on purpose (the control) and left the import alone.
  
  So the move is an unneeded drive-by, though worth a nit at most.

The scratch worktree is removed and `git status --porcelain` is empty.

**Decision: file R1 as a question and R2 as a suggestion. Set aside R3 to R8.**

**R1 is filed as a question, not a blocker.** The agent's point holds, and it removes the reason my earlier notes gave for not raising it. With the opt-in, `{argon2}` rows are not only upgrades. `HibernateUserDAO.java:111`, `:348` and `:413` write new and changed passwords through the same `Security.encodePassword`, so a prefix count also counts passwords saved after opting in. The INFO line at `HibernateContextDAO.java:382` is the only exact record of an upgrade. The shipped `webapp/src/main/resources/log4j2.xml:56` does print it (`org.openmrs.api` at INFO). The tree has no metrics library: 0 hits for micrometer, MeterRegistry and the like, against 33 hits for the control term on the same search. A missing feature has a softer failure than a crash, the log line partly covers it, and dropping or deferring a criterion is the ticket owner's call. So I can't write a blocking sentence that names what breaks, and it goes in as a question.

**R2 is filed as a suggestion.** Deleting `log.error` (`:388`) leaves the suite green, so half of criterion 3 has no test. The fix points to an existing helper, `MemoryAppender`, which `AuthorizationAdviceHierarchyTest.java:241-251` already attaches. The method says a blind agent should read a recommended fix first, and I couldn't start one here, so that check is still owed.

**Why the rest are set aside:**
- **R3:** it needs both a failed UPDATE and a caller that holds its own transaction. Core's argon2 hashes are at most 126 characters against the 128-character column, and the row is already locked at `:145`. The only caller of `Context.authenticate` in main code is `InitializationFilter.java:1839`, which isn't transactional.
- **R4:** losing the login's writes is the trade-off accepted in the thread (12 Nov). The test shouldn't pin it as if it were a guarantee.
- **R5:** the base already takes the row lock. The guard is a second line of defence: if that lock ever moved, a login could otherwise write the old password's hash over a password changed at the same moment. The javadoc at `:364-366` already describes it honestly, which was the agent's own alternative fix.
- **R6:** Spring's `upgradeEncoding` makes this choice, and the thread decided to rely on it. Encoder configuration belongs to TRUNK-6663.
- **R7:** by design. The shipped bean passes `${security.passwordEncoder:}` (`applicationContext-service.xml:50-52`), and the ticket only asks for upgrades to Argon2id.
- **R8:** only audit fields go stale, and only on the in-memory object. `User` doesn't map the password column (LoginCredential does), so nothing can write the old hash back.

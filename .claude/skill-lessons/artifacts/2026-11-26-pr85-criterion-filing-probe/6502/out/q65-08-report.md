**Filed**
- **R1, question.** The head misses the fifth acceptance criterion as written. The only trace of an upgrade is the `log.info` at `HibernateContextDAO.java:382`. The review thread never discusses this criterion. The method says to ask rather than block when the ticket's purpose may be met, since what the ticket meant is for its author to say. "Can be exposed" is loose wording, and the log line is a partial way to track upgrades. So I downgraded the blind agent's "blocking" call to a question.
- **R2, question.** My own mutation showed the gap: removing the `log.error` leaves the tests green, so nothing checks the "an error is logged" part of the third criterion. The thread never covered it. A fix I recommend needs a blind refuter first, and I can't start one, so the method says it ships as a question.

**Set aside**
- **R3:** You already accepted the inline approach on the reasoning that core's argon2 hashes are at most 126 characters and `users.password` holds 128. That rules out a failed UPDATE, which is the only trigger. The only core caller of `Context.authenticate` is `InitializationFilter.java:1839`. I did not reproduce this one; I set it aside because no shipped setup reaches it.
- **R4:** Losing the writes is an accepted cost, not something the PR promises. A test that pins it would lock the defect in.
- **R5:** The guard is reachable. `authenticate` takes the lock with `select user_id … for update` and then reads the password with a separate plain `select`. When the login joins a caller's transaction, its `READ_COMMITTED` setting doesn't apply. On MySQL, that plain read can return an old snapshot from before a committed password change, and the guard then refuses to overwrite the new password. This is reasoned from the code, not run: it needs MySQL access.
- **R6:** This is Spring's `upgradeEncoding` behaviour. ibacher's comment 3856352698 told the author to defer to Spring, and encoder configuration belongs to TRUNK-6663.
- **R7:** The ticket asks only for upgrades to Argon2id. With no encoder opted in (`idForEncode` is `""`), `upgradeEncoding` returns false for unprefixed hashes by design.
- **R8:** `User` maps `date_changed` but not `password` (`User.java:135`). The stale values exist only in memory, and any later save of that user re-stamps them through `AuditableInterceptor.onFlushDirty`.

- **R4 (the failure test can't see the lost writes):** A test that saw them could only pin that the writes are lost. That loss is the accepted trade-off, and the test would go red when the behaviour improved.
- **R5 (the `AND password = :oldHash` guard):** The premise is wrong. The lock is `select … for update`, but the password is read by a separate plain `select`. When `authenticate` joins a caller's transaction, Spring ignores its `READ_COMMITTED`. The `transactionManager` bean doesn't set `validateExistingTransaction`. On MySQL's default REPEATABLE READ, that plain select can return an old hash. The conditional UPDATE always checks the current row, so it stops an old password being written over a newer one.

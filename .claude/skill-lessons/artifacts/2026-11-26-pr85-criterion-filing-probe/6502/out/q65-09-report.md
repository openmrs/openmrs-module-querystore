I've decided all eight: three get filed (R1 as a question, R2 as a suggestion, R5 as a nit) and five are set aside. Nothing was built, posted or staged, and `git status --porcelain` is clean.

**R1, the counter (question, not blocking).** No acceptance criterion in the head counts upgrades. The only trace of one is the `log.info("Successfully upgraded password hash for user: {}", user)` line in `upgradePasswordHash`, and nobody in the review thread mentions the metric. The ticket says only that a counter "can be exposed", which could mean a log line is enough. The method says that when the purpose might already be met, I ask rather than block, so it goes on that line as a question. I also couldn't name a caller that breaks, which a blocking comment would need.

**R2, untested error log (suggestion).** The mutation from my own pass stands. The only test covering a failed upgrade, `authenticate_shouldStillLogInWhenTheUpgradeFails`, checks that the login returns, that one encode was attempted and that the hash is unchanged. It never checks the log, so the "an error is logged" half of the third criterion has no test. The test tree already has a way to capture logs: `LoggingAdviceTest` attaches `org.openmrs.logging.MemoryAppender`.

**R5, unreachable guard (nit).** I finished the part my own pass had left. `authenticate` locks the row with `select user_id from users where user_id = ?1 for update` before it reads the password. Between that read and the UPDATE, the only calls are role and property hydration, `setLastLoginTime`, `saveUserProperties` (`session.update(user)`) and `encodePassword`. None of them writes `users.password`: only `LoginCredential.hbm.xml` maps that column, and `authenticate` never loads a `LoginCredential`. So `AND password = :oldHash` can't be reached in production. The test that covers it only works because its stand-in encoder writes to the database from inside `encode()`. The javadoc already says the guard covers only a same-session change, so this stays a take-or-leave nit.

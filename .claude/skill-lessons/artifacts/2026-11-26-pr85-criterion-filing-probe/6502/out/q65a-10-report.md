**R1, filed as a question** on `HibernateContextDAO.java:382`, the `log.info("Successfully upgraded…")` line. The head does miss the fifth acceptance criterion as written, and no thread in the review conversation discusses it. My earlier reason for not raising it doesn't hold. That reason was that the count can be read from `users.password LIKE '{argon2}%'`, but new passwords go through the same encoder: `HibernateUserDAO.java:111` (saving a user) and `:348` and `:413` (changing a password) all call `Security.encodePassword`. Once argon2 is turned on, that query counts every password saved or changed since, not just the upgraded ones. So the only real trace of an upgrade is the INFO line. I didn't make it blocking for two reasons. The words "can be exposed" leave it open whether the ticket wants a counter or only the ability to count, and the method leaves that reading to the ticket's author. Also, 2.8.x has no metrics library to report a counter through: no micrometer or metrics entry in either pom, and the same search does find `openmrs-api`, so the search works. My earlier pass should have caught this when it checked its own claims against facts it already had.

**R2, filed as a suggestion** on `:388`, the `log.error` line. `ContextDAOTest` never checks the log: searching it for `Failed to upgrade`, `log.error` and `Appender` finds nothing, while the same search finds `MemoryAppender` in six other test classes. Together with my earlier finding that deleting `log.error` leaves the suite green, nothing tests the "an error is logged" half of criterion 3.

**Set aside**

That same reason rules this case out. The only production caller, `InitializationFilter.java:1839`, doesn't run inside a transaction.
- **R4 (failure test can't see the lost writes).** A test that sees them would pin the accepted loss, which neither the ticket nor the PR promises to keep.
- **R5 (redundant guard).** The method's "a guard nothing reaches is a nit" rule doesn't apply cleanly here. When `authenticate` joins a caller's transaction, Spring ignores `READ_COMMITTED`. On MySQL's REPEATABLE READ the plain password select could then read a snapshot older than the `for update` lock, and the guard would catch that. I worked that out but didn't run it, so I won't ask for a safety clause to come out.
- **R6 (parallelism-only change never re-encodes).** That is Spring's `upgradeEncoding`, which the maintainer told the PR to build on (25 August comment), and encoder settings belong to TRUNK-6663.
- **R7 (SHA-1 rows never upgraded to SHA-512 by default).** The ticket only asks for upgrades to Argon2id, and the opt-in default is TRUNK-6663's decision.
- **R8 (stale audit fields on the returned `User`).** Only the object in memory is stale. The whole-PR agent's committed argon2 login left `date_changed` set to that day and `changed_by` set in the database. `AuditableInterceptor.onFlushDirty` (`AuditableInterceptor.java:76`) re-stamps both fields on any later dirty flush, and the login path changes only user properties, never roles.

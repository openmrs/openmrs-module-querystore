R2 gets filed as a non-blocking suggestion about the missing test, limited to TextHandler and BinaryDataHandler. R1, R3 and R4 are set aside. I changed no files, and `git status --porcelain` is empty.

**R1, set aside.** On master, `getPath()` also checks the legacy location first. So `purgeData` on master also deletes only the legacy copy, and later reads fall through to the current copy. The data still being readable after a purge is therefore old behaviour, not something this PR adds. What the PR does change is which copy a read returns *before* a purge. That only matters if a key exists in both locations, and nothing in core creates that state:
- New keys come from `BaseStorageService.newKey`, which uses a date plus 8 random characters under `<appdata>/storage`.
- Legacy obs keys are 2.7-style `<title>_<uuid>` names under `<appdata>/complex_obs`.

**R2, filed as a suggestion.** The second reviewer is partly wrong here:
- **BinaryStreamHandler hasn't changed.** On master it already wrapped every read error, `IOException` included, in `APIException` (`catch (Exception e) → throw new APIException("Obs.error.while.trying.get.binary.complex", …)`).
- **The exception change in Text and BinaryData isn't a problem.** ibacher asked for it in thread 3990887402 ("throw an APIException wrapping the IOException"). That thread is outdated, so the comment goes on the head lines and links to it.
- **The missing test is real.** Searching `api/src/test` for `trying.get.complex` finds nothing, and neither `TextHandlerTest` nor `BinaryDataHandlerTest` mentions `APIException`. The same search did find the `assertThrows` in `BinaryStreamHandlerTest`, so it isn't missing matches. If the new `throw` were dropped, the failure would go back to "Complex data must not be null" without the original cause. I didn't run a test with the throw removed, so the comment says only that no test asserts this.

**R3, set aside.** The supported extension point is `StorageService` itself: a bean picked through `storage.type` and its `@Qualifier` (`StorageServiceCondition`). That is still covered, because the new `default getDataWithMetadata` builds on `getData` and `getMetadata`. Core has no subclass of `LocalStorageService` or `S3StorageService` outside tests (the only one is `CountingLocalStorageService` in a test). Overriding a single read method on a concrete service bean relies on internal call paths the interface never promised.

**R4, set aside.** This is my own open thread 4512249216. At the head, the author has applied my suggestion as written: the two-argument overload now has `@Deprecated(since = "3.0.0")` and points to the three-argument one. Under the method, a real fix gets no further comment.

I decided on all four: two get filed as questions or suggestions, and two are set aside.

- **R3 is filed as a question.** It's real. Reads in the handlers go through `getDataWithMetadata`, and `LocalStorageService` and `S3StorageService` now implement that method themselves without calling `getData`. So a subclass that overrides `getData`, for example to decrypt, is silently skipped when an obs is read. Modules can register their own storage bean through the `storage.type` qualifier (`StorageServiceCondition`), and both classes are public and not final, so extending them is a supported path. I can't name a module that actually does this, so the method makes it a question. It has the same shape as the `injectMissingMetadata` point, but nothing would warn an overrider here. If such subclasses are supported, a Javadoc note on `getData` pointing them to `getDataWithMetadata` covers it.
- **R2 is filed as a suggestion, but only the missing test.**
  - The switch to `APIException` is what ibacher asked for: thread 3990887402 says to throw an `APIException` wrapping the `IOException`, and 3990880262 questions the `Assert` line.
  - `BinaryStreamHandler` is not a change at all: master already threw `APIException` from its `catch (Exception e)`.
  - What's left is coverage. `TextHandlerTest` and `BinaryDataHandlerTest` have no `assertThrows` or `APIException`, and no test anywhere uses the new `Obs.error.while.trying.get.complex` message. The same search does find the `assertThrows` in `BinaryStreamHandlerTest`, so it isn't missing hits. Without such a test, going back to swallowing the error would leave everything green. ibacher's thread is outdated, so this would be a fresh comment on the `TextHandler` catch.
- **R1 is set aside.** New keys are `<obsDir>/<timestamp><8 random chars>-<filename>` (`BaseStorageService.newKey`). Legacy keys are `<obsDir>/<title>_<uuid>.<ext>`. So one key exists in both places only if someone copied the files, which means the two copies are identical. In that case the change only decides which identical copy a read serves. Purge deletes the legacy copy and leaves the other one behind, and master's `purgeData` does exactly the same through `getPath`.
- **R4 is set aside.** It's the user's own open thread 4512249216, and at this head the two-argument overload carries `@Deprecated(since = "3.0.0")` with the suggested Javadoc and delegates to the new overload. The fix is in, so the method says to stay quiet.

I didn't run a build. Everything above comes from reading the code and searching it.

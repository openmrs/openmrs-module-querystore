**Decision:** I'm filing three of the four. R1 goes in as a question, R2 as a suggestion and R3 as a question. R4 is set aside because an earlier round of mine already raised it and the head applies that fix.

- **R1, filed as a question.** On master, `getData` and `getMetadata` both went through `getPath`, and `getPath` tries the legacy location first. Reads and purges therefore always hit the same file. At this head, `read()` in `LocalStorageService.java` tries the current location first. `purgeData` still goes through `getPath`, which is unchanged and legacy-first. So when both copies exist, a read returns a different copy than master did, and a different copy from the one a purge deletes. Both copies can exist when a legacy obs (key `complex_obs/<title>_<uuid>.<ext>` after `parseDataKey`) is copied into `<appdata>/storage/complex_obs/` without the original being removed. The second reviewer reproduced this. I can't show the condition never happens, so under the method it goes in as a question that names the condition, not set aside. No existing thread covers it.
- **R2, filed as a suggestion, cut down to what holds.** On master, a non-missing `IOException` in `TextHandler` and `BinaryDataHandler` was logged and swallowed, and `Assert.notNull` then threw `IllegalArgumentException`. Now it's an `APIException` that wraps the cause. ibacher asked for exactly this change in thread 3990887402 ("throw an APIException wrapping the IOException"), so I'm not questioning the exception type. I'm filing only the missing test: `git grep` finds no test in `api/src/test/java/org/openmrs/obs/` that hits that path. The `BinaryStreamHandler` part of R2 is wrong. Its `catch (Exception e)` already threw `APIException` on master, so nothing changed there.
- **R3, filed as a question.** Both classes are public and not final, with public constructors. No production subclass exists in the tree; the only one is a test helper in `LocalStorageServiceTest.java`. At the head, the S3 `getData` itself delegates to `getDataWithMetadata`, so overriding `getData` has no effect on reads in either backend. For example, a subclass that decrypts in `getData` would now hand back the stored bytes, and nothing would fail. Downstream modules are out of reach here, so I can't show the condition never happens, and it stays a question.
- **R4, set aside.** I raised this myself in thread 4512249216 on 2026-11-09, asking for the two-argument `injectMissingMetadata` to be deprecated so the compiler flags overrides. `AbstractHandler.java` at the head carries that exact `@Deprecated(since = "3.0.0")` with the pointer. The method says a real fix gets silence.

I didn't change any files, and `git status --porcelain` is clean.

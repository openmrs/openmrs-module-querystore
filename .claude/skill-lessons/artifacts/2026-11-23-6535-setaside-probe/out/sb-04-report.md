**R1, filed as a question on the `getPath` Javadoc in `LocalStorageService`.** I checked this against the code. On master, reads and `purgeData` both went through `getPath`, which prefers the legacy copy, so they always handled the same file. At this head, `read()` tries the current location first, while `purgeData` (lines 254–275) still calls `getPath`. So when a key has a file in both places, reads return the current copy and purges delete the legacy one. That also changes which copy users see compared with master. Both copies existing is unusual: it could happen if an upgrade copied legacy files into `storage/` without deleting them. The method says a defect reachable through data an installation can hold is filed as a question that names the condition, so that's how it goes in.

**R2, filed as a suggestion, in a new comment that links ibacher's thread.** Moving to `APIException` is what ibacher asked for on `BinaryDataHandler` ("throw an APIException wrapping the IOException"), so the type change itself isn't raised. The coverage gap is real, though. A grep finds no test that triggers a non-missing `IOException` in the Text, BinaryData or BinaryStream handlers. The only new negative test checks `NoSuchFileException` at the storage level. If someone merged the two catch blocks back into one that swallows everything, it would bring back greptile's "masks storage failures" problem and no test would fail. It isn't blocking because nothing is broken today. ibacher's thread is outdated, so the method puts this in a fresh comment on the head lines rather than a reply there.

**R3, set aside.** Nothing in the tree subclasses `LocalStorageService` or `S3StorageService`. The way to plug in other storage is a separate `StorageService` bean selected by `StorageServiceCondition` on its `@Qualifier`, and those beans get the new `getDataWithMetadata` default, which calls `getData` and `getMetadata`. A subclass of a concrete bean that overrides `getData` can also override `getDataWithMetadata`. And going around `getData` is exactly what the ticket's single combined read requires.

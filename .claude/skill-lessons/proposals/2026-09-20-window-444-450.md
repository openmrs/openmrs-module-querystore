## P1 · `pr-harden` Step 1 — "check it out detached" binds only an agent with its OWN checkout

**The lesson.** Step 1 tells every reviewer brief to name the round's sha "and has the agent check it
out detached". An agent without `isolation: "worktree"` shares the orchestrator's checkout, so that
`git checkout` moves the HEAD the run commits from — which is the shared-worktree hazard `harden`
Phase 2 documents and this skill's own **State** section forbids ("DO NOT EDIT THE WORKTREE WHILE A
DELEGATED AGENT IS RUNNING").

**Corroboration.** Bar (a), three records, and the ledger's own reopen condition met twice:
`REJECTED.md`:2234-2237 parked this at **1 record** (#247, "a cleanup detour") with "**REOPEN ON:** a
second record."
- #446: "briefing the reviewer to 'check out detached' left MY worktree detached; the next phase's
  fixer then edited in detached HEAD and the branch had to be reattached before committing.
  Reattaching also hit a leftover agent worktree holding the branch (`--ignore-other-worktrees` was
  needed). Rounds 2 and 3 briefed 'the worktree is already at the head — do not check out anything'
  and the problem did not recur."
- #444: "Round 1's reviewer died on a 429 and left the worktree DETACHED because I had not passed
  `isolation: 'worktree'`. Every later round used it."
- #247 (already on the ledger): the detached tree also held the branch, so a later `git checkout
  <branch>` failed twice.

**The edit** — replacing the paragraph that begins "**A brief names that SHA and has the agent check
it out detached.**":

> **A brief names that SHA, and only an agent with its OWN checkout is told to check it out.** The
> round's ref name is a shared resource: on #370 two reviewers in isolated worktrees could not `git
> fetch origin pull/371/head:pr-371` because a sibling agent's worktree already held that name, and
> briefing the SHA fixed it at no round or cycle cost. But a `git checkout` by an agent that has no
> checkout of its own lands on the tree this run commits from — on #247 that tree then held the branch
> and a later `git checkout <branch>` failed twice; on #446 the next phase's fixer edited in detached
> HEAD, and reattaching had to get past a leftover agent worktree holding the branch
> (`--ignore-other-worktrees`); on #444 a reviewer that died on a 429 left it detached, and every
> later round passed `isolation: "worktree"`. So either isolate it, or brief that the worktree is
> already at the head and nothing is to be checked out — #446's rounds 2 and 3 took the second and the
> problem did not recur.

**What a refuter should press.** That isolation is not free in the other direction: #445 records "an
isolated fixer cannot push to the pipeline worktree (the harness refuses git operations against
another worktree), so its edits had to be extracted as a patch" — so this must not read as "isolate
the fixer too". Whether #247's remedy ("return the worktree to `<branch>`") is a third option the edit
drops, and whether dropping it loses a measured rule.

## P2 · `pr-harden` State — the polling decision is made at the SPAWN, not at the collection

**The lesson.** The rule reads "Collecting in the same turn means never polling afterwards" and argues
the cost of `TaskOutput`. Three runs in one window polled anyway, and the reason is structural rather
than inattentive: once an `Agent` call carries `run_in_background: true`, `TaskOutput` is the ONLY way
to collect it, so by the time the rule applies the cost is already committed. The rule bites at the
spawn and does not say so.

**Corroboration.** Bar (a), three records.
- #445: "An agent launched with run_in_background:true can only be collected by polling TaskOutput,
  and each poll injects a 32 KB window of raw JSONL. Fixed mid-run by switching to
  run_in_background:false for the fixer, reviewer 2 and the verifier — their reports came back whole,
  in one result each. The first two agents cost ~10 polls between them."
- #447: "TaskOutput polling on agent tasks is very expensive (~25-30k tokens per timed-out poll, raw
  JSONL windows). Six polls across three agents cost more than every agent report combined."
- #448: "Three TaskOutput calls on background agents each injected a truncated window of raw JSONL
  (~20k tokens apiece) before the rule's reasoning was applied."

**The edit** — one sentence into the "Collecting in the same turn" paragraph:

> **The choice is made at the SPAWN: do not pass `run_in_background: true` to an `Agent` call.** After
> that call there is no cheap collection left, because `TaskOutput` is the only one there is. Three
> runs of one window paid the cost before acting on the rule — #445 switched the fixer, reviewer 2 and
> the verifier to foreground mid-run and their reports "came back whole, in one result each", after
> the first two had cost ~10 polls; #447 spent six polls across three agents, "more than every agent
> report combined"; #448 spent three at ~20k tokens apiece.

**What a refuter should press.** Whether it contradicts the existing sentence "Where you need to block
on something that is NOT an agent — a build, a server coming up — that is a background Bash task" (it
should not: that is `Bash`, not `Agent`). Whether #448's own escape — "a foreground poll on a
terminal-state predicate over the transcript, which costs nothing and reads no content" — belongs in
the edit; it is one record, and `harden` already warns that a transcript file is not a report.

`REJECTED.md`, parked entry *"pr-harden's cap raised nine times on a change where each fix legitimately
opens the next defect in the same area"* (#339, 13 rounds over ~16h): rounds 8–11 found no behavioural
defect and round 12 then found a real one (366 duplicate chips over 610 products), so "any rule
stopping after four quiet rounds would have shipped it." Its reopen condition is stated explicitly:

> **REOPEN ON: a signal that separates this from spinning, not a cap.**

Two further reasons, either sufficient:

1. #298's stated ground is *symmetry* — a claim about two documents, not evidence about outcomes. The
   bar in skill-retro Step 3 is not met by it at all.
2. A cap is a weakening of Termination, so it must pass the standing counterweight in `REJECTED.md`
   (*"The confirming-cycle rule, as POSITIVE evidence"* — #229: "every one of the last seven passes
   found exactly one real defect, all prose, each in a file the change had not edited. Six of them
   would have shipped under any 'it's basically converged' stop. **Any future proposal to weaken
   Termination has to pass this.**"). A cap of 4 stops #229's run before six of those seven.

**Record as re-derived-and-killed**, so a third derivation does not cost a future retro the same walk:
#298 derived it, this pass derived it again independently.

## P-C · LIVE: `harden` is not a subset of `pr-harden`, and two runs took the override believing it was

**The finding.** `harden` ends on a labelled override in 6 recorded runs (#268 c3, #269 c1, #284 c1,
#293 c6, #317, #337 c1). In two of them the *stated reason is structural rather than cost*:

- `…-268.md:59` — override "taken at cycle 3 **because pr-harden supplies the same adversarial pass
  with a fixer and verifier attached**."
- `…-337.md:27` — "took the labelled override after cycle 1 rather than spending a full confirming
  cycle **ahead of pr-harden, which is a stronger gate**."

**That premise is false, and #229 is what refutes it.** #229's seven late passes each found one real
defect, "all prose, **each in a file the change had not edited**." `pr-harden`'s reviewer reviews the
pushed head — a diff-scoped review. A defect in a file the change never touched is structurally
outside its reach; this is the same blindness `harden` names in its own Phase 1 ("Diff-scoped review
structurally cannot catch these: the stale code never appears in the diff, so it is never read").

So the two gates are **complementary, not ordered**. `pr-harden` is the stronger gate for the code the
PR changed, and `harden`'s late cycles are the only gate for everything the change *invalidated
without touching*. "pr-harden runs next and is stronger" is a valid reason to skip a cycle only for
the first class.

**Bar (Step 3): met — the lesson appears in two or more run records** (#268, #337 state the false
premise; #229 supplies the fact that refutes it).

**Proposed edit** — one clause in harden's Termination, beside the override, and nothing else:

> The override is a **cost** valve. "`pr-harden` reviews next and is the stronger gate" is not a
> reason to take it: that loop's reviewer is diff-scoped, so it cannot see the class these late cycles
> find — #229's last seven passes each found one real defect, all prose, each in a file the change had
> not edited. The two gates are complementary, not ordered.

**Step 4 — what it prunes / renders stale.** It adds ~4 lines and prunes none, so it owes a
justification: it *strengthens* an existing rule by removing a recorded false reason for evading it,
rather than adding a new obligation. It also reframes (does not retire) the parked entry *"harden's
confirming-cycle cost against where the blocking findings come from: 3 records"* — that entry weighs
harden's cycle cost against pr-harden's blocking findings, and P-C says the two counts are not
commensurable because they cover different defect classes. **Count stays 3; the reframing is a note,
not a decrement.**

**Known weaknesses, stated for the refuter.**

- It is textual, and the ledger's most repeated meta-lesson is *instruction-is-not-the-lever*: 15
  incidents / 12 records of `git checkout` losing work "AFTER the rule was written, correctly placed."
  A clause telling runs not to use a bad reason may simply not bind.
- It does not reduce harden's cost, which is the pressure actually producing the overrides. It may
  convert 2 labelled overrides into 2 more full cycles, which is a cost nobody has measured.
- #269, #284, #293 and #317 took the override for reasons this clause does not address, so at most 2
  of 6 override runs are reached.

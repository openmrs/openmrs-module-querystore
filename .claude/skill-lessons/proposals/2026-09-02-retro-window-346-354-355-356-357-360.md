## P1 · `pr-harden` — state that the commit-first rule outranks "one commit per round"

**Claim.** The skill mandates "One commit per round" (`pr-harden`:82 in the round table, :509 in the
COMMIT step) and separately mandates committing before anything mutates the worktree, "before you
delegate, and before your OWN measurement probe" (:784-785). A round in which a probe is run, or in
which a delegated agent dies leaving partial work, cannot satisfy both. Nothing in the document says
which yields.

**Corroboration limb: clause 3 (a skill contradicting itself), one sighting sufficient.**
`2026-09-02-chartsearchai-355.md`, "Where a skill blocked or contradicted this run", bullet 1:
"pr-harden:'one commit per round' vs 'commit before anything mutates the worktree' — round 2's fixer
died mid-phase on a 429 with partial work in the tree; committing it before retrying (correct)
produced two commits for that round. The commit-first rule should say it outranks the one-commit
convention."

**Proposed edit** (`pr-harden`, COMMIT step, after :509's "One commit per round…"): one sentence
saying a commit taken mid-round to protect work — before a probe, or over a dead agent's residue —
is expected and does not violate this; what the convention actually protects is append-only history,
which such a commit does not touch.

**Prune answer.** Subsumes nothing; retires nothing. Net +2 lines, justified as the class-3 limb:
the contradiction is a fact about the document, and the run had to resolve it by reasoning rather
than by reading.

**Not a re-proposal.** `REJECTED.md` has killed two remedies in the neighbouring `git checkout --`

restore idiom for a `cp` aside (2026-08-24 P1). Neither is a precedence clause between two commit

## P3 · `gate-state` + `harden` — `--count-edits` implements the per-run reading its own docstring rejects, whenever an upstream exists

**Claim.** `count_edits` (`~/.claude/pipeline/gate-state`:127-160, mirrored at
`.claude/pipeline/gate-state`) states its own design in its docstring: *"Per-cycle rather than
per-run on purpose. The run's own total (`HEAD --not --remotes`) does not return to zero while
nothing has been pushed, so it would block the stop at the close of a pre-PR cycle that changed
nothing."* Its first branch is `if <upstream exists>: return dirty + count(@{u}..HEAD)`, which is
exactly a per-run reading that does not return to zero while nothing has been pushed. The recorded
per-cycle head (`since`) is consulted **only** when there is no upstream. `harden`:284-288 repeats
the same framing — "both halves, because a cycle that commits its work has still changed something".

**Corroboration limb: clause 3 (a skill contradicting its own gate script), one sighting sufficient
— plus one record measuring the consequence.**
`2026-09-02-…-357.md`: "harden:Termination — `--count-edits` counts unpushed commits on a branch
with no upstream, so cycle 8 read `edits=16` at convergence and only reached 0 after the push. The
gate would have blocked a genuinely converged run." (The record's own attribution of the branch is
inverted — the run's branch had an upstream, which is the branch that produces this — and the
proposal rests on the code and the docstring, not on the record's diagnosis.)

**Proposed edit.** In `count_edits`, prefer the recorded head whenever one is available, and fall
back to `@{u}..HEAD` only when there is none — which makes the function measure per-cycle in both
configurations, as its docstring already says it does. The fallback over-counts, which asks for a
cycle rather than allowing a stop, so the failure direction is unchanged. Update the docstring and
`harden`:284-288 to say which reading applies when.

**Prune answer.** Deletes `harden`:288's justification clause "because a cycle that commits its work
has still changed something" as the false generalisation (Step 4's prefer-deletion), and the
docstring's now-wrong "With an upstream the commit half is `@{u}..HEAD`". Net ≈ +1.

**Open question for the refuter.** Should this be a code change at all from one record, or only a
documentation fix naming the remedy the run used (push, re-count, then override)? Argue both.
